# Adopt Playwright screenshot comparison as the shared visual regression testing approach

**Context:** This org builds a fighting game engine and its surrounding tooling — visual correctness (a stage composing correctly, a character's sprites/animations placed correctly, a lifebar rendering correctly, an in-match frame looking right) is a first-class concern, not a nice-to-have. Today, "real-browser verification" (driving a real headless Chromium via Playwright, screenshotting, and eyeballing the result) is already the org's established practice for confirming a rendering feature actually works — every one of `character-viewer-web`, `character-editor`, `stage-viewer-web`, `stage-editor`, `lifebar-viewer-web`, `lifebar-editor`'s own `docs/testing.md` documents exactly this kind of pass. But it is entirely manual and ad hoc: none of these repos has Playwright installed as a dependency, nothing is committed as a repeatable test, and nothing runs in CI. A concrete real-world case shows the cost: `stage-viewer-web` shipped a rendering bug (a stage's `[StageInfo]` `xscale`/`yscale` never applied, so any hi-res-authored stage renders its BG sprites ~8x oversized, filling/overflowing the canvas with an unrecognizable crop) that every unit test and the `stage` library's own real-file corpus scan missed completely, because none of them ever look at a rendered pixel — the data parsed fine, the bug was purely visual. Nothing short of an actual image comparison would have caught it.

**Decision:** Adopt **Playwright's built-in screenshot comparison** (`expect(page).toHaveScreenshot()` / `toHaveScreenshot()` on a locator) as the shared visual regression testing tool, rather than a bespoke pixel-diff integration or a third-party visual-testing service. This turns the org's existing informal "real-browser verification" practice into a real, committed, automated test suite instead of introducing a new tool or discipline from scratch.

- `web-ui-kit` owns a thin, shared Playwright config/helper — consistent fixed viewport size, CSS animations/transitions forced off, a font-loaded wait, and the project's default diff threshold — that every consuming app's own visual test suite imports, the same "shared primitive, per-app consumption" shape already established for i18n (`.vibe/decisions/023`) and undo/redo/keyboard-shortcuts.
- Each of `character-viewer-web`, `character-editor`, `stage-viewer-web`, `stage-editor`, `lifebar-viewer-web`, `lifebar-editor`, and `mode-quick-versus`'s **web build** gets its own visual test suite covering that app's real rendering surfaces (loaded from real/representative fixture data, not blank/default state), plus `web-ui-kit` itself gets component-level snapshots of its own shared Web Components — catching a shared-token/style regression before it cascades into every consumer.
- Baseline (golden) images are generated once against Linux/Chromium (the same platform CI runs on) and committed to each repo — never generated on a contributor's own OS and committed blind, since cross-OS font hinting/antialiasing is a well-known false-positive source for this kind of test.
- Runs as its own CI job/script (`npm run test:visual`), separate from `npm test` (mirroring the existing "beyond the unit test suite" split each repo's `docs/testing.md` already documents) — but now an **actual required, blocking CI gate**, not a manual dev-time-only pass. A failing diff attaches the actual/expected/diff images to the CI run. Updating a baseline is always its own deliberate `--update-snapshots` commit, reviewed as a diff like any other change — never silent.
- `mode-quick-versus`'s native (Go/`go-gl`+SDL2) desktop build is a distinct rendering stack with no DOM/Playwright surface — out of scope for this decision, same exclusion shape as `.vibe/decisions/023`'s native-localization carve-out; tracked as its own scoping question in that repo's backlog if/when it becomes a priority, not left silently uncovered.
- `engine` is explicitly out of scope — it is a headless combat-simulation library with no rendering output of its own (`.vibe/decisions/004`, `008`); the class of bug this decision targets only ever surfaces at whichever app actually draws pixels, so that is where the tests belong.

**Reason:** Playwright is already the org's de facto real-browser tool (referenced throughout every viewer/editor repo's testing docs) — adopting its own built-in screenshot comparison costs no new dependency and no new mental model, just turning an already-trusted manual practice into a committed, repeatable one. The i18n rollout already proved the "shared primitive in `web-ui-kit`, consumed identically by every app" shape works cleanly across this exact set of repos, so reusing it here avoids re-deriving a rollout pattern. Most directly: this decision is a direct response to a real incident (the `stage-viewer-web` `xscale`/`yscale` bug) that no other layer of testing in this org — unit tests, WASM-bridge fixture tests, or the `stage` library's own real-file corpus scan — was capable of catching, because all of them stop short of ever looking at a rendered pixel.

**Rejected alternatives:**
- **A bespoke pixel-diff integration (e.g. `pixelmatch`/`odiff` wired up by hand per repo)**: rejected — Playwright already ships an equivalent, well-maintained comparison (also `pixelmatch`-based under the hood) with baseline management, CI reporting, and an update workflow built in; hand-rolling the same thing eight times duplicates work for no benefit.
- **A third-party visual-testing service (Percy, Chromatic, Applitools)**: rejected — introduces an external paid dependency with no precedent elsewhere in the org (see `.vibe/decisions/023`'s equivalent rejection of a translation-management SaaS for the same reason), for capability (cloud-hosted baseline review UI) this org doesn't currently need over a committed-in-repo image diff.
- **Relying on `engine`'s state assertions (positions, hitboxes, damage) instead of ever rendering pixels**: rejected — proven insufficient by the actual incident motivating this decision: the underlying data was completely correct, only the rendering was wrong. State-level tests and pixel-level tests catch different, non-overlapping bug classes; this org needs both.
- **Generating baselines per-contributor's own OS**: rejected — a known source of flaky false-positive diffs from font/antialiasing differences across platforms; baselines are always Linux/Chromium, matching CI.
