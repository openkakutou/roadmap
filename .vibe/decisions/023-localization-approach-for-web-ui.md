# Adopt i18next as the shared localization approach for every web UI app

**Context:** No repo in the org handles localization today — every UI string across the seven web apps (`character-viewer-web`, `character-editor`, `stage-viewer-web`, `stage-editor`, `lifebar-viewer-web`, `lifebar-editor`, `mode-quick-versus`) and the shared `web-ui-kit` design system itself is hardcoded English, with no i18n/l10n infrastructure anywhere in the workspace. Left to each repo independently, this would produce seven divergent ad-hoc translation mechanisms and a duplicated locale-switcher UI, directly against the pattern the org already follows for other cross-cutting concerns (shared design tokens, undo/redo, keyboard shortcuts) via `web-ui-kit`.

**Decision:** Adopt **i18next** (+ `i18next-browser-languagedetector`) as a shared external dependency for UI string translation, rather than building a bespoke translation primitive. `web-ui-kit` owns a thin, shared integration layer: centralized i18next configuration (init, per-repo namespace convention, browser-language detection with a localStorage-persisted override) plus a `<wuik-locale-switcher>` Web Component, mirroring the existing pattern of pairing a headless primitive with a Web Component UI (`ShortcutManager` + `<wuik-shortcuts-panel>`, `CommandStack`). Each consuming web app owns its own namespaced JSON message catalogs (`src/i18n/en.json`, `src/i18n/fr.json`) loaded into that shared i18next instance. Initial supported locales are English (source/default) and French, enough to validate the mechanism end-to-end; more locales are added incrementally later without any architecture change. `mode-quick-versus`'s native (Go/SDL2) desktop build is a distinct rendering stack with no DOM/JSON string loading — it is explicitly out of scope for this decision and tracked as its own scoping backlog item in that repo instead of being left undecided indefinitely.

**Reason:** i18next is the most mature and widely adopted library for this exact problem (interpolation, pluralization, namespaced/lazily-loaded JSON catalogs, browser language detection) — reimplementing it as a bespoke primitive would duplicate work the ecosystem has already solved well, for no benefit specific to this org's needs. It is framework-agnostic and does not conflict with `web-ui-kit`'s "no framework dependency, ever" principle, which targets UI frameworks (React/Vue/etc.) that would force a different component model than native Web Components — a string-translation library carries no such constraint. The Product Owner explicitly authorized an external dependency for this case. Centralizing the integration in `web-ui-kit` (rather than each app configuring i18next independently) keeps the locale-switching UI and detection/persistence logic consistent across all seven apps, following the same shared-primitive-plus-component shape already proven for undo/redo and keyboard shortcuts.

**Rejected alternatives:**
- *Bespoke, dependency-free translation primitive built in `web-ui-kit`* — rejected: reinvents a well-solved problem (interpolation, pluralization, catalog loading, language detection) for no gain over an established library, once an external dependency is permitted.
- *FormatJS (`intl-messageformat`) or Lingui* — rejected: viable alternatives, but a smaller ecosystem and/or heavier build-time tooling (Lingui's macro/compiler step) than i18next for a plain JSON-catalog, no-framework use case; i18next's lighter integration surface fits the vanilla Web Components stack more directly.
- *Each app integrates i18next independently, with no shared `web-ui-kit` layer* — rejected: would duplicate locale-switcher UI and detection/persistence logic across seven repos, the same problem this decision's shared-component pattern already avoids elsewhere.
