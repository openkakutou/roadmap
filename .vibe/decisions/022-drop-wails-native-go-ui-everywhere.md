# Drop Wails entirely: native Go UI for every native target, no webview anywhere in the org

**Context:** Decision `021` adopted Wails (native Go backend + the existing TypeScript/`web-ui-kit` frontend rendered in the OS's webview) once the core stayed Go. The Product Owner pushed back: a webview still isn't free — a JS engine, DOM/CSS layout, and a JS↔Go bridge marshaling every call are real overhead, particularly unwelcome for `mode-quick-versus`'s real-time HUD/match rendering. The stated priority is being as close as possible to the available optimizations, without being locked into someone else's engine or rendering abstraction — consistent with `engine` itself being a from-scratch combat simulation, not a wrapper around an existing one.

Two pieces of research grounded the decision:
1. **Ikemen GO** (the org's own reference implementation for MUGEN/Ikemen compatibility) uses exactly this shape: `go-gl/gl` (raw OpenGL bindings) + `veandco/go-sdl2` (SDL2 for windowing/input/context) — no game-engine abstraction on top, no webview. SDL2, unlike GLFW, supports Android (and iOS), which is why Ikemen GO ships Android builds at all — though even there, desktop OpenGL vs. Android's OpenGL ES is a real gap Ikemen GO itself only closes via a translation layer ([gl4es](https://github.com/ptitSeb/gl4es)) that lives partly as a community fork, not fully mainlined.
2. A spike (`mode-quick-versus/benchmarks/render-lang-spike/`, 2026-08-16) compared raw `go-gl`+SDL2 against Ebiten on an identical sprite-draw workload (200 sprites/frame), same swap/vsync settings on both sides, under headless Xvfb + Mesa llvmpipe software rendering (no GPU available in the spike's environment). Result: **go-gl+SDL2 averaged ~1.51 ms/frame vs. Ebiten's ~11.76 ms/frame — roughly 7.8× faster** on this workload. Caveat: software-rendering only (absolute numbers don't reflect real hardware), and Ebiten's overhead here is partly attributable to its pure-Go X11 client (`XGB`) vs. SDL2's native C X11/GLX bindings — a Linux/X11-specific factor that may not generalize identically to Windows/Mac. Directionally, though, it confirms raw bindings meaningfully outperform a general-purpose game framework for this org's draw-call-heavy pattern.

**Decision:** Wails is dropped. No webview anywhere in the org, on any native target. Each app now gets a from-scratch native Go UI, matched to what it actually needs:
- **`mode-quick-versus`**: native Go + `go-gl` + SDL2 (Ikemen GO's own stack) for Windows/Mac/Linux/Android. Android needs its own resolution of the desktop-GL-vs-GLES gap (tracked as backlog `010`, replacing the now-moot Wails-Android-maturity item, backlog `009`) — not assumed solved by adopting SDL2 alone.
- **`character-editor`/`stage-editor`/`lifebar-editor`**: native Go + [Fyne](https://fyne.io/) for Windows/Mac/Linux (no mobile target for the editors, per decision `019`). Fyne over Gio (immediate-mode, lower-level, more building-blocks-not-widgets) specifically because these are forms/panels apps (property editors, sprite browsers, palette editors) with no real-time constraint — Fyne's ready-made widget set (forms, lists, buttons, scrolling) directly fits that shape and is faster to build against, where Gio's finer control answers a performance question these apps don't have.
- **Web** (all four apps): unchanged — still the existing TypeScript/`web-ui-kit` frontend, WASM-loaded `character`/`stage`/`sff`/`engine`, deployed to GitHub Pages. A browser can't run native Go UI code either way, so this target was never in scope for this decision.

**Consequence, stated plainly:** every app now maintains **two separate UI implementations** — the existing TypeScript/`web-ui-kit` one (web) and a new native Go one (desktop/mobile: SDL2/OpenGL for the game, Fyne for the editors) — not one shared frontend wrapped differently, which is what every prior packaging decision in this thread (`015`, `019`, `020`, `021`) had assumed. This is a real, ongoing maintenance cost (two codebases per app to keep in sync feature-wise), accepted here in exchange for native performance and no framework/webview lock-in on the platforms where that matters.

**Reason:** Matches direct, repeated Product Owner direction (performance and control over the org's own game-engine work take priority over one-shared-frontend convenience) and now has supporting evidence (the spike) rather than resting on preference alone. Matched per-app rather than uniformly: `mode-quick-versus` has an actual real-time constraint justifying raw bindings; the editors don't, so a batteries-included widget toolkit (Fyne) serves them better than either a webview or a bare-metal graphics API.

**Rejected alternatives:**
- *Wails everywhere* (decision `021`) — superseded: doesn't remove the webview/bridge overhead the Product Owner explicitly objects to, even though it was the right call once Rust was ruled out for the shell.
- *Ebiten for `mode-quick-versus`* — rejected per direct Product Owner statement ("je construis un moteur de jeu, le but n'est pas d'en utiliser un autre") and confirmed by the spike: Ebiten measurably slower here, and its abstraction is exactly the kind of dependency this decision avoids.
- *Gio for the editors* — considered, not chosen: philosophically closer to "no heavy framework," but the editors' actual need (CRUD-style forms) is served faster by Fyne's ready-made widgets; Gio's low-level control isn't a need these apps have.
- *SDL2+OpenGL for the editors too, matching `mode-quick-versus`* — rejected: would mean hand-building form widgets (text fields, lists, scroll, dialogs) from primitives for no performance benefit these apps require.
